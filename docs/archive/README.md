## 怎么判断一份文档该不该归档

| 信号 | 处理 |
|---|---|
| 描述的是**当前**在跑的架构 | 留在 `docs/` 根目录 |
| 描述的是**将来要建的**架构（且还没建） | 归档，但要在正文顶部写明「未实现」 |
| 记录的是**决策过程 / 踩过的坑** | 见下方特殊约定 |
| 完全零引用、零信息量 | 直接删，git 历史留着就够 |

## 特殊约定：踩坑记录不要归档

**`docs/Pitfalls.md` 曾经躺在 `docs/v2/00_Legacy_Pitfalls_and_Guidelines.md`。**

V2 架构最终没有实现，看着像废弃文档 —— 但它列的坑**现在还在犯**。
所以它被提升到了 `docs/Pitfalls.md`，并加上了「现状」一栏。

> 教训：架构设想废弃了，**教训不会**。
> 判断一份文档能不能归档，看的是「它记录的东西是否还有效」，
> 而不是「它服务的那个架构是否落地了」。

## 归档不等于删除

所有归档内容都还在 git 历史里，随时可以翻出来。
需要找回某份文档时：

```bash
git log --diff-filter=D --name-only -- <路径>   # 找出它什么时候被删/移走的
git show <commit>^:<路径>                        # 把它取回来
```
